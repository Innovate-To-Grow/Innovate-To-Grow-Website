# Code scanning

CodeQL (`codeql.yml`), Semgrep (`ci.yml`, SARIF uploaded from `main`) and Trivy (image scans) report to the
repository's Security tab (`security/code-scanning`). This page says how an alert is handled and records the
triage of the backlog.

## How an alert is handled

1. **A real weakness, or something that can be made strictly safer without changing behaviour, is fixed in
   code**, with a test that pins the property. The alert closes on its own when the next scan of `main` no
   longer reports it.
2. **A false positive is dismissed in the Security tab with the reason `false positive` and a comment that
   says why**, so the next person does not re-triage it. Semgrep's default registry includes rules for other
   stacks (Java/JSF, SQLAlchemy) and generic-text rules whose `...` spans at most ten lines; those produce most
   of the noise. `# nosemgrep: <rule id>` keeps the CI gate green (`Semgrep SAST` honours SARIF suppressions),
   but **GitHub ignores in-source suppressions**, so an alert for a suppressed finding still has to be
   dismissed, and the comment should say the suppression exists.
3. **A deliberate design is dismissed as `won't fix`** with the reasoning (for example a `csrf_exempt` endpoint
   that is cross-origin by design and protected another way).
4. Test fixtures and helpers that the rule mistakes for application code are dismissed as `used in tests`.

Dismissals are done with the API so the reason is recorded:

```bash
gh api -X PATCH repos/Innovate-To-Grow/Innovate-To-Grow-Website/code-scanning/alerts/<n> \
  -f state=dismissed -f dismissed_reason='false positive' -f dismissed_comment='<why, 280 chars max>'
```

Trivy findings in the backend image are fixed with a Debian package floor under `src/security/debian/`
(one package per file; the Dockerfile installs and verifies them).
